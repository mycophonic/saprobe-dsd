# Implementation Notes

## DSD-to-PCM Pipeline

### Architecture

saprobe-dsd converts DSD bitstreams to PCM in two stages:

1. **Stage 1 — 8:1 byte-level decimation.** A 96-tap symmetric FIR filter (Gesemann design) converts each DSD byte (8 bits) into one float64 sample. For DSD64 at 2,822,400 Hz this produces 352,800 Hz output directly. For higher DSD rates the output is at the byte rate (DSD128 → 705,600 Hz, DSD256 → 1,411,200 Hz).

2. **Stage 2 — Cascaded halfband 2:1 decimation.** Zero or more symmetric FIR halfband filters (127-tap Parks-McClellan design), each halving the sample rate. DSD128→352.8k uses one halfband stage, DSD256→352.8k uses two, etc.

The special case DSD64→705.6k uses a 4:1 bit-level converter (63-tap FIR) instead.

### Origins and Prior Art

The stage 1 filter is Sebastian Gesemann's [dsd2pcm](https://code.google.com/archive/p/dsd2pcm/source) (2009, BSD license). It is the de facto reference implementation for DSD-to-PCM conversion. The same 96-tap filter is used by:

- **ffmpeg** — incorporated into [`libavcodec/dsd.c`](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/dsd.c) by Peter Ross (2014)
- **dsd2dxd** — [extended fork](https://github.com/clone206/dsd2dxd) with alternative filter options
- **dBpoweramp** — DSD decoder plugin
- **foobar2000** — SACD input plugin

The filter is documented as: flat response up to 48 kHz, stopband rejection ~160 dB, 17 microseconds delay. Designed for 44100×64 Hz input with downsampling factor of 8.

### Comparison with ffmpeg

#### Stage 1: Identical Filter

Both saprobe and ffmpeg use the same Gesemann 96-tap symmetric FIR filter. The apparent difference in tap count is a storage convention:

- saprobe stores 48 right-half coefficients in [`tables.go`](../internal/dsd/tables.go) (`htapsCount = 48`), exploiting symmetry during convolution.
- ffmpeg stores 48 right-half coefficients in [`dsd.h`](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/dsd.h) (`HTAPS = 48`), precomputing byte-level lookup tables for speed.

The effective filter is identical in both implementations: 96 taps, same coefficients, same frequency response. The difference is purely in execution strategy — ffmpeg trades 6 KB of lookup table memory for fewer runtime multiplications.

#### Stage 2: Different Decimation Strategies

For DSD rates above DSD64, the stage 1 output must be further decimated to reach the target PCM rate. This is where saprobe and ffmpeg diverge.

**saprobe — purpose-built halfband cascade:**

Each stage is a 127-tap symmetric halfband FIR (Parks-McClellan / Remez design, generated by [`generate_filters.py`](../internal/dsd/generate_filters.py)). Halfband filters exploit the property that every other coefficient (except the center tap) is zero, halving the number of multiplications per output sample. The cascade is optimal for power-of-2 decimation ratios, which is exactly what DSD rates produce (DSD128→352.8k = 16:1 = 8:1 × 2:1, DSD256→352.8k = 32:1 = 8:1 × 2:1 × 2:1). All intermediate values are float64.

**ffmpeg — general-purpose polyphase resampler:**

After the DSD decoder produces output at the byte rate, ffmpeg's `libswresample` handles any further sample rate conversion. This is a polyphase resampler designed for arbitrary rate ratios (e.g. 48000→44100). For power-of-2 decimation it works correctly but is not specifically optimized for this case — it carries the overhead of a general-purpose design. All values are float32.

#### Summary

| Property | saprobe | ffmpeg |
|----------|---------|--------|
| Stage 1 filter | Gesemann 96-tap symmetric FIR | Gesemann 96-tap symmetric FIR |
| Stage 1 storage | 48 right-half coefficients, direct convolution | 48 right-half coefficients, 6 KB lookup tables |
| Stage 2 filter | 127-tap halfband FIR (Parks-McClellan) | `libswresample` polyphase resampler |
| Stage 2 design | Purpose-built for 2:1 decimation | General-purpose arbitrary rate conversion |
| Intermediate precision | float64 | float32 |
| Odd-length handling | Floor (discard trailing sample) | Ceiling (zero-pad, produce extra sample) |

The 1–2% RMS difference at DSD128 and ~5% at DSD256 come entirely from the different stage 2 implementations and intermediate precision. Stage 1 contributes no difference.

### Why Halfband Cascade

The halfband cascade is the textbook multistage decimation architecture for power-of-2 ratios (Crochiere & Rabiner, *Multirate Digital Signal Processing*). Its advantages:

1. **Computational efficiency.** Halfband symmetry zeroes out every other coefficient, halving multiplications. A 127-tap halfband needs only 32 multiply-accumulates per output sample.

2. **Passband flatness.** A halfband filter with -100 dB stopband rejection inherently achieves ±0.0001 dB passband flatness, a property of the symmetric frequency response around Fs/4.

3. **Relaxed transition band at each stage.** Each 2:1 decimation doubles the transition band relative to the signal bandwidth, allowing shorter filters at later stages. In practice saprobe uses the same 127-tap filter at every stage since the computational cost is already low.

The main alternative for stage 1 is a CIC (Cascaded Integrator-Comb) filter, common in hardware/FPGA implementations because it requires no multiplications. CIC introduces passband droop that must be compensated by a subsequent FIR stage. For software, the direct FIR approach (Gesemann) is simpler and avoids the droop/compensation overhead.

### Sample Count: Floor vs Ceiling Decimation

When a halfband stage receives an odd number of input samples, it must decide how to handle the unpaired trailing sample. Two valid approaches exist:

1. **Floor (discard):** Output `n / 2` samples, ignoring the trailing input sample.
2. **Ceiling (pad):** Implicitly zero-pad the input to even length, output `(n + 1) / 2` samples.

saprobe uses floor decimation. The trailing sample is discarded rather than paired with a synthetic zero.

ffmpeg uses ceiling decimation through its resampler (`libswresample`). When the DSD decoder produces an odd number of intermediate samples, the resampler flushes its internal filter state with implicit zero-padding, generating one additional output sample.

#### Why floor is correct for DSD

The extra sample produced by ceiling decimation is a filter artifact: the halfband filter's output at that position depends on future input samples that don't exist. Zero-padding substitutes silence for missing data, contaminating the output with the filter's impulse response to the zero/signal boundary. For a symmetric FIR halfband with 127 taps, this artifact extends over ~63 output samples at the filter's operating rate.

Floor decimation avoids this entirely. The cost is one fewer output sample — approximately 2.8 microseconds of audio at DSD128, or 0.7 microseconds at DSD256. This is inaudible and below the resolution of any DAC.

#### Empirical verification

Tested across DSD128 (DFF and DSF containers) and DSD256 (DSF) files:

| Condition | Sample count difference (saprobe − ffmpeg) |
|-----------|---------------------------------------------|
| Even DSD byte count | 0 (exact match) |
| Odd DSD byte count | −1 (saprobe produces one fewer sample) |

The −1 difference occurs only when the DSD byte count per channel is odd, causing the halfband input length to be odd after 8:1 decimation. Files with even byte counts match exactly.

### ffmpeg DSD Pipeline Reference

ffmpeg's DSD-to-PCM conversion is split across three components:

1. **Container demuxer** ([`dsfdec.c`](https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/dsfdec.c), [`iffdec.c`](https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/iffdec.c)): Reads DSF or DSDIFF containers. Sets `sample_rate = DSD_rate / 8`, presenting the DSD stream at its byte rate (e.g. DSD128 → 705,600 Hz).

2. **DSD decoder** ([`dsddec.c`](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/dsddec.c), [`dsd.c`](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/dsd.c)): 8:1 decimation via the Gesemann 96-tap FIR, stored as 48 right-half coefficients ([`dsd.h`](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/dsd.h): `HTAPS = 48`) with precomputed lookup tables. `ff_dsd2pcm_translate()` produces one float per DSD byte. No further decimation occurs inside the codec. Frame sample count is `avpkt->size / ch_count` (integer division, no padding).

3. **Resampler** (`libswresample`): When the user requests a different output rate (e.g. `-ar 352800`), the resampler performs additional decimation. Output count uses ceiling: `ceil(in_count * out_rate / in_rate)`. This is where the +1 sample difference originates for odd input counts.

### Empirical Divergence

| DSD Rate | RMS difference | Peak difference | Source |
|----------|---------------|-----------------|--------|
| DSD128 | 1.2–2.1% | 1.1–2.5% | Stage 2 filter + float64 vs float32 |
| DSD256 | 5.0–5.1% | 4.7–4.9% | Compounds across two halfband stages |

Higher DSD rates show greater divergence because each additional halfband stage compounds the difference between saprobe's 127-tap halfband and ffmpeg's polyphase resampler. These differences are within the normal range for independent DSD-to-PCM implementations — there is no standard algorithm, and audible differences at these levels are negligible.
